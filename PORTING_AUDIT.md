# Current Android implementation audit

This document is a technical walkthrough of the code at HEAD. It intentionally contains no historical comparison, resolved-bug narrative, or planned feature claims. [AGENTS.md](AGENTS.md) is the operational guide, [DEVELOPMENT_HANDOFF.md](DEVELOPMENT_HANDOFF.md) is the dated cross-agent snapshot, and this file explains execution paths. Reinspect code if HEAD or versions change.

## Startup and ownership graph

1. Android creates `CookieRunBotApplication`; `onCreate()` initializes `PersistentTrace`, OpenCV, `BotRuntime`, `TelegramCommandReceiver`, and runtime diagnostics.
2. `MainActivity` attaches a `BotController.Listener`, renders runtime/capture diagnostics, and launches the system MediaProjection consent intent.
3. Successful consent calls `ScreenCaptureService.start()`. The foreground service builds `StateDetector`, starts `ScreenCaptureManager`, creates `BotControlOverlay`, and schedules idle MAINMENU detection every 750 ms. That idle detector explicitly exits while `BotRuntime.isRunning()` to avoid a competing OpenCV pass.
4. `BotRuntime` owns exactly one `BotController` using application context. Activity detach only removes the UI listener. `ScreenCaptureService.shutdownResources()` dismisses the bubble, stops the bot, closes detector/capture resources, and marks capture stopped.
5. The overlay builds/persists `BotOptions`; Start invokes `BotRuntime.start(options)`, while Stop invokes `BotRuntime.stop()`.

## Capture-to-action trace

`ScreenCaptureManager.start()` obtains MediaProjection and registers callbacks. A dedicated capture thread owns ImageReader/VirtualDisplay resources. `acquireLatestImage()` prevents backlog; the plane's row/pixel strides are copied into a tight reusable RGBA Mat. Current display size and cutout insets produce a `ContentTransform`; `FrameNormalizer.normalize()` crops its 16:9 `contentRect` to 1280×720, with the opt-in Redfinger profile using pixel-equivalent `copyTo` only for an exact `(0,0,1280,720)` content rectangle rather than resizing. Both raw and normalized Mats are supplied to `LatestFrameProvider.updateFrame()`, which copies only the latest normalized frame, publishes dimensions/timestamps/FPS/transform, increments generation, and wakes waiters.

Consumers receive cloned ownership through `snapshot()` or `awaitNextSnapshot(afterGeneration, timeout)`. `StateDetector.detectFirst()` converts the screen to reusable grayscale storage, creates each ROI submat, and evaluates loaded template variants using normalized correlation. A match is `score >= 0.8`. Legacy uses the seven configured scales for GAME_START and GAME_RELAY; the opt-in Redfinger profile evaluates only native scale 1.0, omits GAME_START after successful handling for that round and defers expensive detailed IN_GAME NO_MATCH score reports without changing normal detection. Detection results contain stage, score, ROI-relative location, and selected template size. See [REDFINGER_PERFORMANCE_PROFILE.md](REDFINGER_PERFORMANCE_PROFILE.md).

A handler requests a logical gesture through `ActionExecutor`. `CoordinateMapper` uses the current `ContentTransform` to map normalized detector/action coordinates into the physical display. `GestureArbiter` grants a single lease; `BotAccessibilityService.dispatchGesture()` reports initial acceptance and later invokes completion/cancellation. `GestureCompletionContext` releases the lease on callback, cancellation, or timeout. Workflows that need visual proof establish their baseline after successful completion and wait for `generation > baseline`.

The deliberately isolated **Legacy** paths that bypass `CoordinateMapper` are the three `POST_RELAY_*_PHYSICAL` points calibrated for 2400×1080, TIME_DEAL's absolute physical `(2000,70)` tap, and PARTY_RUN_SEASON_REWARDS' absolute physical `(1260,980)` tap. Redfinger instead maps the calibrated post-relay logical `(1198,35)`, `(647,425)`, `(637,389)` points through current content geometry, and blocks TIME_DEAL/PARTY_RUN_SEASON_REWARDS until manual popup clearance rather than guessing physical coordinates. Other actions use normalized logical coordinates; the Legacy exceptions remain device-dependent.

## Controller loop and groups

`BotController.start()` creates a new statistics session and run generation, initializes PRE_GAME state, scheduler/watchdog/popup/no-match fields, and submits `runLoop()` to a single executor. `waitForReadiness()` requires capture running, advancing/fresh frames, Accessibility setting enabled, live service instance, and service connection. The loop owns one `StateDetector` until stop.

- PRE_GAME and POST_GAME poll the current latest snapshot and sleep 120 ms between ticks.
- IN_GAME blocks on `awaitNextSnapshot(lastGeneration, 500)` and therefore processes only newly published latest frames.
- Every tick rechecks run, recovery gate, capture, Accessibility, maximum 1-second frame age, previous-results settling, and minimum fresh generation.
- `detectFirst()` uses ordered lists from `stagesFor()`. ALWAYS (`CONNECTION_LOST`, `INACTIVE`) is checked in all normal groups. Relic stages are removed when the option is off.
- No match produces throttled score diagnostics. With debug saving enabled, `NoMatchWatchdog` asks the capture publisher for the next raw/normalized pair and writes it asynchronously; it never triggers taps/restarts/Telegram.

### Current stage order

- PRE_GAME after ALWAYS: `LOGIN`, `CONGRATULATIONS`, `LEVEL_UP`, `RELIC_COMPLETE`, `RELIC_CLAIM`, `DAILY_CHECKIN`, `DAILY_CHECKIN_BOOST_SET`, `DAILY_TREASURE`, `DAILY_NEW`, `ENTER_LEAGUE`, `LEAGUE_RESULTS`, `PREVIOUS_RANK_RESULTS`, `TOO_MANY_TREASURES`, `PARTY_RUN`, `PARTY_RUN_SEASON_REWARDS`, `TIME_DEAL`, `PREVIOUS_RESULTS`, `GAME_SETTINGS`, `MAINMENU`, `PURCHASE_ITEM`.
- IN_GAME: `GAME_RELAY`, `GAME_COMPLETE`, `GAME_START`, then ALWAYS. `LOGIN` is excluded from this primary path and appears only in the background/recovery rotation after primary misses. The temporary Fast Start path checks `GAME_START`, then ALWAYS, so Login is not scanned during that priority window. In opt-in Redfinger mode a GAME_START already handled in that round is omitted from subsequent scans, and native scale 1.0 is used for GAME_START/GAME_RELAY; Legacy retains the seven-scale behavior.
- POST_GAME after ALWAYS: `ANTI_BOT`, `OVERTAKE_BREAK_SCORE`, `MYSTERY_BOX`, `LOGIN`, PRE_GAME reward-popup stages in their existing order, and `MAINMENU`.

## Main gameplay trace

- **MAINMENU:** `revalidateMainMenu()` waits for a newer frame, scans ALWAYS and blocking PRE_GAME states, and confirms MAINMENU again. It aborts stale work if another screen wins. Pending scheduled/test Friend Life begins here. Quick Lives may run for a completed round. Start Game is tapped only after applicable workflows and another safe revalidation.
- **PURCHASE_ITEM:** optional desired boost taps the random item and scans the fixed boost region on fresh frames for up to 30 seconds. The controller then taps Play, increments/initializes the round, marks post-game life work, enters IN_GAME, opens the Fast Start window, and starts jump automation.
- **GAME_START / GAME_RELAY:** configured owned actions are tapped once per relevant state. Optional post-relay action sequence uses isolated Legacy physical targets or the Redfinger profile's calibrated logical targets, according to the snapshotted profile. Fixed-count/continuous jump taps are managed by `GameAutoTapper` and stop on lifecycle/state exits.
- **GAME_COMPLETE:** detection resets progress and commits POST_GAME before result handling. After its current settle time, the collector receives a clone for asynchronous score/coin/XP analysis. A newer frame must still match GAME_COMPLETE before Finish. Optional result saving reads its preference live.
- **POST_GAME:** Mystery Box saves/classifies and updates the existing round; reward screens are dismissed by specialized or generic handlers. Popup actions use callback/fresh-frame gates where required, return to generic group scanning rather than a predicted chain, and guard unchanged fingerprints against repeated taps.
- **Recovery states:** Connection Lost and Inactive tap Reload. Login is primary in PRE_GAME/POST_GAME and background/recovery-only in IN_GAME; it is not in ALWAYS. `LOGIN_1.png` is matched at scale 1.0 with the standard 0.8 threshold in normalized ROI `Rect(390,570,500,130)`; the handler taps `(match.x + width/2, match.y + height/2)`, waits 5,000 ms, and taps logical `(657,294)` on the Google logo with zero jitter. It then runs a Login-only fresh-frame probe for `LOGIN_ACCOUNT_PICKER_1.png` at threshold 0.8 in `Rect(270,75,740,210)` for at most 60,000 ms. A match triggers the fixed logical profile-circle tap `(323,299)` with zero jitter; a rejected profile dispatch keeps searching within the remaining minute. Timeout performs no additional tap. Both success and timeout end the Login flow and resume PRE_GAME; only the successful profile tap installs a fresh-frame baseline. Accepted Login taps remain limited to once every 3 seconds. Anti-bot chooses detected odd cards. Between Anti-bot tests, six mean-normalized card-interior fingerprints are compared both globally and per slot. The existing global-change rule is preserved; additionally, a same-artwork shuffle qualifies only when moved slots closely match artwork from other baseline slots and those mappings form a real permutation cycle. Any qualifying layout must then remain stable on two fresh frames before the next test is accepted. This catches shuffled layouts that previously fell below the whole-layout ratio without broadly treating two selected-card highlights as a new test. If a follow-up remains continuously matched with no successful Anti-bot card tap or accepted new layout for 60 seconds, `AntiBotStallRecoveryTracker` allows an emergency path only after three newer frames still match ANTI_BOT while Connection Lost and Inactive do not. That path bypasses only the layout-transition guard and still calls the ordinary odd-card detector and logical tap code. It is disabled after Test 3 while waiting for challenge exit; an emergency attempt with no successful tap restarts a full 60-second window instead of retrying immediately. When the controller is already following Test 1 or Test 2, the accepted follow-up is recorded in the same three-test statistics challenge even if more than two minutes elapsed; round changes, backwards timestamps, and a completed Test 3 still force a new challenge. No handler force-stops/restarts an app.

The League-ended restart notice has its own detector state, `LEAGUE_ENDED_RESTART`. Its supplied 564×211 text template matched the normalized 1280×720 reference frame at `(350,181)`; runtime search uses the bounded ROI `(330,160)-(934,412)` at scale 1.0. It stays out of primary IN_GAME candidates and `ALL_STAGE_ORDER`, but is now included in the low-frequency IN_GAME background/recovery rotation. A background match is stored and rechecked on a strictly newer frame before dispatch; the existing popup-instance guard prevents repeated taps on an unchanged popup. Confirm is tapped at `(640,458)` with zero jitter. After the tap, the generic callback/fresh-frame machinery waits for a new frame and routes through PRE_GAME detection to establish the resulting menu/restart state.

## Friend Life and Quick Lives audit

`FriendLifeScheduler` separates schedule state, manual test state, in-progress state, and retry-not-before. Scheduled work becomes pending after the configured interval (1–1440 minutes, default **61**) from Start Bot, but starts only from revalidated MAINMENU. Failed scheduled work remains pending with a 15-minute delay; completed work schedules from completion time. A manual test is queued, coalesced with a scheduled trigger when appropriate, rejected if stopped, and reported if already queued/in progress. Its read-only dashboard status exposes the current schedule/retry/progress without rescheduling.

The controller obtains fresh scans of top/bottom/send ROIs. Top search uses bounded upward naturalized paths; traversal uses bounded downward paths. Every accepted swipe waits for callback success, establishes a post-callback generation baseline, obtains a fresh frame, and asks `FriendScrollVerifier` whether the verification ROI actually changed. Send transactions scan interrupts between Send and both confirmations; there is no extra post-CONFIRM_2 button-disappearance verification. A successful Send-button gesture callback records game progress immediately, without waiting for later confirmations. A successful `CONFIRM_1`, `CONFIRM_2`, or orphan-confirm gesture resets the independent high-confidence stuck-Confirm tracker, so a later popup starts its own 60-second episode. Separately, during ordinary PRE_GAME/POST_GAME detection, once that tracker is active and another state matches, the controller waits for a strictly newer frame and rechecks full-frame `CONFIRM_SEND_LIFE_1.png` at 0.95 before any state action. If Confirm persists it is tapped first and normal detection waits for the post-gesture path; if absent, the tracker resets and the earlier state match is discarded for fresh redetection. Safety decisions are based on visual progress, 30-second no-progress time, 10-minute top search, and 30-minute absolute traversal time.

Quick Lives is a separate mailbox transaction enabled per-round. It uses `ALL_LIVES_RECEIVED_AND_SENT_1`, `NO_LIVES_TO_RECEIVE_1`, and confirmation templates/policies, its own callback/fresh-frame checks and 120-second bound. Its flags and scheduler state are not shared with Friend Life.

## Watchdog and recovery audit

`GameProgressWatchdog` is generation/reservation based. `GameProgressWatchdogManager.start()` creates a scheduled single-thread checker, records BOT_START, and checks every 30 seconds. The only subsequent progress reasons are confirmed GAME_COMPLETE and successful Friend Life SEND_BUTTON gesture. At 15 minutes overdue, it independently reserves recovery and alert work.

The alert captures the latest normalized snapshot, optionally PNG-encodes it, and submits asynchronously to Telegram. Delivery is committed only on HTTP success; failure schedules eligibility 5 minutes later. A successful alert suppresses more alerts until new progress starts another episode.

Recovery is handed to `BotController` and executed on its recovery executor. A current run/reservation check activates `ProgressRecoveryGate`, blocking normal dispatch. The first bounded loop scans the full normalized frame for `CONFIRM_SEND_LIFE_1`, tapping its detected logical center (radius 5) no more than three times. No match ends that loop immediately; successful gestures must receive a callback and a strictly newer post-gesture frame, with a 2-second continuing-attempt delay. **After this confirm loop ends for any reason (not found, disappeared or three taps), recovery proceeds to the CLOSE_BUTTON_1 stage.** The Close stage searches the top-right quarter using the ordinary grayscale `StateDetector.detectTemplate()` / `TM_CCOEFF_NORMED` path and threshold 0.8; it does not call the alpha-mask SQDIFF helper. It stops on no-match or after three matched taps. Both stages require successful gesture completion and a strictly newer frame; the final matched tap skips retry delay but still requires a fresh frame. Gesture/frame failure aborts this recovery episode rather than acting on stale evidence. Recovery then tests the resulting frame and successive fresh frames for MAINMENU for at most 120 seconds; a match routes to PRE_GAME. Completion clears only the matching reservation/gate.

## Configuration and UI audit

`BotOptions` validates tap interval 100–1000 ms, positive fixed jump count, and the dependency of post-relay sequence on Cookie Relay. `BotOptionsStore` persists all overlay fields in SharedPreferences. Start takes an immutable option snapshot. Debug/result image switches also write immediately and are read dynamically by save sites; other edited controls require a new Start to affect the controller.

`MainActivity` is a programmatic diagnostic screen and includes the non-Telegram **Update App** button; `BotControlOverlay`, `StatisticsActivity`, `DebugLogActivity`, `TelegramSettingsActivity` and `UpdateActivity` are also programmatic UI. There are no layout XML files. Statistics refresh every second without changing session state. Debug Log supports copy/clear/save (500 RAM lines), Save 10h ZIP and the optional incident-video toggle. Telegram settings support enable, token/Chat ID, image/text preferences, save, and a manual test message. The update screen handles an owner-configured anonymous HTTPS feed or Android document-picker APK import; both install paths require user confirmation and will not silently stop a running bot or capture.

GitHub Actions includes a manual `Cleanup Artifacts` workflow. It first paginates and collects every artifact ID, then deletes those IDs with the workflow-scoped `GITHUB_TOKEN` granted `actions: write`; this avoids pagination shifting during deletion. It leaves workflow runs/logs and repository files untouched.

## Statistics, storage, and diagnostics audit

`RoundResultCollector` owns one analyzer executor and snapshots `RoundResultStore.sessionGeneration()`. It uses `ResultNumberDetector` and `MysteryBoxClassifier`; results from an old session generation are discarded. `RoundResultStore` synchronizes access, retains 50 recent rounds, and maintains aggregate contribution records so replacement updates contribute only a delta. It separately tracks the current-session distribution of confirmed rounds with exactly 0–5 boxes (zero only after a successful completed scan) across all rounds, not just the latest 50; late classification/replacement subtracts the old bucket and adds the new one. Telegram `/stats` (and therefore `/all`) displays these five counts. `SessionRuntimeFormatter` is presentation-only and is shared by the Statistics summary, overlay Session Time, and Telegram `/stats`: it switches at 24 hours to day-aware text while the underlying `sessionRuntimeMs` continues monotonically within the session. Round-duration and Watchdog formatting remain separate.

`PublicImageStore` uses MediaStore/public collections on modern Android and legacy public paths where applicable. Results go to `Pictures/CookieRunBot/results`; no-match pairs go to `Pictures/CookieRunBot/debug`. `DebugLogStore` bounds memory at 500 messages. `RuntimeDiagnosticsLogger` emits throttled health/DETECT_STALL context. `PersistentTrace` writes/rotates an app-specific cold-start trace. None of these diagnostic signals authorize recovery actions beyond the explicitly wired progress watchdog.

## Calibration window rotation audit

`CoordinateCalibrationOverlay` owns a standalone `TYPE_APPLICATION_OVERLAY` view hierarchy. Previously the panel width/height were fixed at `showPanel()` from the then-current display geometry, with `FLAG_LAYOUT_IN_SCREEN`. Switching away from the landscape game could rotate Redfinger to portrait without refitting that WindowManager view, clipping right-hand controls. The new panel uses a display-specific Window Context where available; configuration and DisplayManager callbacks request an immediate and delayed reflow using `CalibrationPanelLayoutPolicy.fit()` against the current system-bar/cutout-adjusted window bounds. It no longer forces `FLAG_LAYOUT_IN_SCREEN`.

The persistent **✕ Close** header is outside the scrollable form. Closing unregisters callbacks, cancels pending reflows, removes the window, and restores the parent bubble. A layout-update failure also closes safely. This resize path leaves `LatestFrameProvider`, screenshot selection, `CalibrationCoordinatePolicy`, saved points, detector, templates, and Accessibility gestures untouched. A rotated display does not alter the captured frame's original `ContentTransform`; the UI prompts a fresh explicit capture to obtain current physical coordinates. See [CALIBRATION.md](CALIBRATION.md).

## Telegram audit

`TelegramConfigStore` stores nonsecret settings in SharedPreferences and delegates token encryption to `TelegramSecureTokenStore` (AES-GCM with an Android Keystore key); it migrates a legacy plaintext preference if encountered. `TelegramNotifier` uses a single scheduled executor, bounded HTTP timeouts, token-redacted logging, and retry handling for command replies. Gameplay does not wait for it.

`TelegramCommandReceiver` long-polls `getUpdates`, persists update offset and parses only read-only `/help`, `/status`, `/stats`, `/last`, `/boxes`, `/all`, `/friend`, `/health`, `/screen`, `/watchdog`, `/rounds`, `/errors`, `/update`, `/logs`, `/dashboard` (plus dashboard `/start`/`/menu` aliases). Incoming commands require the configured Chat ID; replies capture a hash identity of the authorizing token plus Chat ID and cancel delayed/retried sends if current settings differ. `TelegramDashboardPolicy` provides a persistent reply keyboard; All/Refresh map to `/all`, Update App to `/update` and Download Logs to `/logs`. `TelegramNotifier.sendCommandAll()` attempts a fresh normalized 1280×720 **PNG file** via Telegram `sendDocument` using the same 15-second cooldown as `/screen`, then sends a separate unchanged stats/status/last snapshot; failed file upload yields a short note but not a lost summary. The dedicated `TelegramScreenshotEncoder` converts a caller-owned RGBA frame clone to an independently allocated BGRA Mat before OpenCV `.png` encoding, releasing intermediates; `TelegramScreenshotMultipart` retains the exact PNG bytes and reply keyboard. Automatic diagnostic/watchdog `sendPhoto` calls and gameplay/capture/detection code remain unchanged. `TelegramDashboardReplies` formats Friend Life/health/watchdog/recent rounds/allowlisted errors. `TelegramUpdateReply` formats version and release-note status using the in-app feed preference. The `/update` command's separate `telegram-apk-delivery` worker then downloads a newer candidate to a dedicated private cache using `UpdateFeedClient.download()` with the 49,000,000-byte transfer cap. It verifies HTTPS/SHA-256/package/version/installed certificate before streamed `sendDocument` multipart upload (chunked HTTP, no whole-APK memory buffer), and rechecks the authorizing token/chat. Single-flight and five-minute successful same-hash cooldown avoid duplicate transfers. It never remotely installs or controls gameplay and cannot block ordinary watchdog Telegram sends. The receiver does not implement gameplay commands.

## In-app update path audit

`UpdateActivity` reads the installed package version and stores the user-supplied HTTPS feed URL in the `robotrun_update` preferences. `UpdateFeedClient.check()` parses the bounded JSON feed, requires matching application ID, and compares numeric version codes. `download()` only follows HTTPS redirects, bounds the APK, compares SHA-256, verifies archive package/version and signing certificate against the installed RobotRun package, and moves the validated APK from temporary storage to the private updates cache. Alternatively, `importLocal()` uses Android's document picker with package/newer version/certificate/size checks (there is no externally published checksum for a manually selected local file).

`RobotRunUpdateFileProvider` grants the Android installer temporary read-only access only to `cache/updates/`. `UpdateActivity` blocks installer launch while Bot or Screen Capture runs, requests Android's install-source permission when needed, and opens an explicit system installation confirmation. It never silently stops or restarts gameplay. Source is private; the example `docs/update-feed.example.json` is a template, not a live release URL. The manually triggered signed debug artifact alone is not a permanent anonymous update channel.

## Overnight Diagnostics source audit

`RobotLog` forwards RobotRun-owned Android Logcat calls without changing their call sites' message or Android log priority. `DebugLogStore` and `PersistentTrace` forward into `OvernightLogArchive`. The bounded 8192-work queue writes UTC epoch-ms-prefixed text to private hourly files, retains an exportable 10h window and limits on-disk text to nominal 200 MiB. `[ARCHIVE_LOSS]` notes rejected/sized-pruned events. A whole hourly file is pruned after falling outside the 10h window; exact export filters by timestamp. The Debug Log's Clear clears only 500 RAM preview lines.

`GameProgressWatchdogManager.check()` reserves a genuine overdue Recovery, then `IncidentManager.begin()` freezes previous 30m text, status and a cloned normalized screenshot before invoking the existing `BotController.performProgressRecovery()` on its original serialized worker. `logDiagnostic()` forwards only `[GAME_PROGRESS_*]` messages into the Incident timeline and adds mapped physical target alongside logical point for action dispatch. Its `finally` notifies `IncidentManager.finish()` with outcome while retaining original `finishRecovery()` path; manual Watchdog tests create a distinct MANUAL_TEST Incident without resetting the real watchdog clock. No video/write work occurs on the detector thread.

`IncidentManager.begin()` snapshots the normalized still and queues essential status/PNG/30m log archive before starting optional image sampling; it never waits for the optional sampler on gameplay/Recovery. `IncidentVideoRecorder` is only a legacy class name: it performs **no** periodic sampling during gameplay and creates **no MP4 for newly triggered Incidents**. Real/manual Incidents use the existing LatestFrameProvider at 480×270 / JPEG q35 nominally every 2 seconds, without pre-roll, max 90 images / 20 MiB. End at min(trigger+3min, recoveryFinished+10s), or earlier on capture stop, sustained pressure, size/image cap or error. Unknown/unhealthy capture (<2 FPS), stale/duplicate frames and a 2s RobotRun-process CPU window >1 single-core equivalent skip optional samples before clone. Samples >250ms wall or >80ms sampler-thread CPU cause a one-tick backoff; ten consecutive degraded ticks stop sampling. This is NOT system-wide Redfinger CPU telemetry. A low-priority worker saves completed `screenshots/*.jpg` atomically, with `images_timing.txt` and `incident_image_status.txt`. Session fencing prevents old stop/tick work from corrupting a new capture session. Essential 1280×720 screenshot, action timeline and Recovery outcome persist independently. Incidents retain up to 72h / separate 200 MiB cap.

`/logs` runs `LogPackageBuilder` on the separate `telegram-log-delivery` executor, rechecking token/chat while streaming `sendDocument`, then deleting temporary ZIP. Exports include `robotrun_10h.txt`, up to five recent Incidents, new JPEG screenshot sequences plus eligible legacy MP4/JPEG evidence under a shared 35 MiB optional-media budget, and a manifest of omissions. Telegram cap is 49,000,000 bytes; local **Save 10h ZIP** bypasses this transfer cap. Stored legacy `.log` text files are presented as `.txt` inside ZIP. No automatic upload or remote gameplay control. See [docs/OVERNIGHT_DIAGNOSTICS.md](docs/OVERNIGHT_DIAGNOSTICS.md) and focused policy/upload/timing tests. Device performance and screenshot-sequence completeness remain unverified until Redfinger testing.

## Build and verification audit

The app module baseline is **v1.1.10 / versionCode 12** and uses Android Gradle Plugin 8.10.1, Kotlin 2.1.20, Gradle wrapper 8.11.1, Java/Kotlin 17, compile/target SDK 36, min SDK 26, Activity KTX 1.10.1, AndroidX Core 1.16.0 (`FileProvider`), OpenCV 4.13.0, and JUnit 4.13.2. Debug signing switches to the `ci` config only when all four signing environment variables are present. Release minification is disabled and no release signing is declared. Ensure future versionCode increments and same installed signing certificate for any APK update.

`.github/workflows/build-apk.yml` is manual. It checks out, prepares Java/Gradle/API 36, restores and validates a secret-backed keystore, runs `./gradlew testDebugUnitTest`, runs `assembleDebug`, verifies the original `app-debug.apk` signature with build-tools 35.0.0, reads `app/build/outputs/apk/debug/output-metadata.json`, and copies the verified APK as `RobotRun-v<versionName>-vc<versionCode>-g<shortSHA>-run<runNumber>-a<runAttempt>-signed-debug.apk`. Upload Artifact uses that stem as the ZIP name and retains it 14 days. The downloaded APK is a byte-for-byte copy; the internal Gradle output and signing process are unchanged.

Use `./gradlew test`, `./gradlew lint`, and `./gradlew assembleDebug`; then perform real-device checks in [ANDROID_TEST_CHECKLIST.md](ANDROID_TEST_CHECKLIST.md). The source changes and static review do not themselves prove the recent Telegram/updater changes built, a feed was hosted, or an Android/Redfinger installation succeeded; report those as unverified until actually run.
